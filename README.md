# Bad Trans

Программное средство анализа транзакционной активности клиентов банка с формированием индивидуальных профилей поведения.

Система принимает операции, автоматически формирует версионированные профили клиентов и сопоставляет новые операции с предшествующей активностью. Для отклонений сохраняются признаки, балл, применённые правила и объяснения; требующие рассмотрения операции попадают в очередь аналитика. Решения аналитика учитываются при последующем формировании базового поведения.

Это учебная система на синтетических данных. Она не проводит платежи; балл отклонения не является вероятностью мошенничества. При недостаточной истории система явно показывает ограниченность оценки.

## Возможности

- Приём отдельных операций и пакетный импорт с проверкой повторных запросов и внешних идентификаторов.
- Демонстрационный источник истории и новых операций, работающий без открытого браузера.
- Автоматические и плановые профили за 7, 30 и 90 дней отдельно для клиента, валюты и направления IN/OUT.
- Статистики сумм, частоты, активности по дням и времени, состава контрагентов, покрытия наблюдений и динамики активности.
- Разделение наблюдаемой активности `observed` и базового поведения `baseline`: подтверждённые нетипичные операции исключаются из будущей базы, но сохраняются в истории.
- Сохранённые версии профиля и сравнение двух совместимых версий: значения, разницы, изменения состава и происхождение данных.
- Пять семейств проверок: сумма, частота, нетипичное время, новый контрагент и изменение активности. Недостаточные данные не подменяются нулевым риском.
- Очередь случаев, назначение аналитиков, комментарии, эскалация, закрытие и повторное открытие, уведомления.
- Снимки отчётов по профилю, операции и периоду; выгрузка PDF, XLSX и CSV.
- Управление сотрудниками, ролями и блокировкой, отзыв сессий, состояние сервисов и инфраструктуры.

## Архитектура и поток данных

```text
Streamlit UI -> Gateway (GraphQL)
                   |-> Auth Service -> Auth PostgreSQL + session Redis
                   |-> Transaction Service -> Transaction PostgreSQL
                   |-> Analysis Service -> Analysis PostgreSQL
                   |-> Case Service -> Case PostgreSQL

Transaction outbox -> Kafka -> Analysis: профиль + оценка
Analysis outbox    -> Kafka -> Case: случай для рассмотрения
Case outbox        -> Kafka -> Analysis: решения аналитика
```

Gateway проверяет сессию, права и входные данные, вызывает владельцев через gRPC и собирает ответ. Он не читает их таблицы напрямую. Сервисы используют собственные PostgreSQL; внешние идентификаторы не превращаются в межсервисные SQL-ссылки. Доставка событий использует outbox, повторные попытки и защиту от повторной обработки. Ошибочные сообщения сохраняются для разбирательства и повторной доставки.

Фоновые задачи и потребители Kafka исполняются внутри соответствующих процессов сервисов. Каждый сервис имеет отдельный контейнер и образ и обновляется отдельно. Один Docker Compose включает 15 контейнеров: шесть приложений, четыре PostgreSQL, Kafka, два Redis, Kafka UI и pgAdmin.

Стек: Python 3.13, FastAPI, Strawberry GraphQL, gRPC/Protobuf, PostgreSQL 17, Kafka 4, Redis 7.4, Streamlit, pytest. Зависимости приложений зафиксированы в `requirements.txt` и `constraints.txt`; версии инфраструктуры — в `compose.yaml`.

## Быстрый запуск в Windows

Нужны Git и работающий Docker Desktop с Linux containers. Для запуска в контейнерах локальный Python не нужен. PowerShell должен разрешать запуск локальных скриптов; при необходимости используйте `powershell -ExecutionPolicy Bypass -File .\run.ps1 -Build`.

```powershell
git clone https://github.com/scarlet-pixet/bad_trans.git
cd bad_trans
.\run.ps1 -Build
```

`run.ps1` создаст `.env` со случайными секретами, соберёт образы и дождётся готовности приложений. При повторном запуске существующие непустые значения `.env` сохраняются. `.env.example` содержит список настроек без реальных секретов.

| Назначение | Адрес |
|---|---|
| Основной интерфейс | http://127.0.0.1:18500 |
| GraphQL / GraphiQL | http://127.0.0.1:18100/graphql |
| Auth HTTP API / Swagger | http://127.0.0.1:18110/docs |
| Kafka UI | http://127.0.0.1:18190 |
| pgAdmin | http://127.0.0.1:18180 |

Учебные пользователи: **manager**, **analyst**, **admin**. Пароль для каждого: **`BadTrans-demo-2026!`**. Пароли БД и pgAdmin генерируются отдельно и отличаются от пароля приложения.

```powershell
.\run.ps1                         # Запуск без обязательной пересборки
.\run.ps1 -Build                  # Пересборка и запуск
.\run.ps1 -Action Status          # Состояние контейнеров
.\run.ps1 -Action Logs            # Последние сообщения журналов
.\run.ps1 -Action Stop            # Остановка с сохранением данных
```

На Linux/macOS можно создать `.env` со значениями для всех шести ключей из `.env.example`, используя независимые случайные строки; JWT_SECRET должен содержать не менее 32 символов. Затем выполнить `docker compose up -d --build --wait`. Скрипты `.ps1` предназначены для PowerShell.

## Как пользоваться и проверить функционал

### 1. Создать поток данных

Войдите как **manager**, откройте **«Источники данных»** и запустите новый поток. Источник создаёт демонстрационных клиентов, счета и сценарные операции, затем продолжает отправку в фоне. Проверяйте состояние и счётчики; при необходимости приостановите поток.

Для собственных записей войдите как **admin**: **«Клиенты и счета»** позволяет создать клиента и его счёт, **«Ввод транзакций»** — зарегистрировать операцию. Операцию также можно отправить через GraphQL; контракт пакетного импорта — `importTransactions` в схеме API.

### 2. Посмотреть индивидуальный профиль

У **manager** откройте **«Профили клиентов»**, выберите клиента, валюту, направление и окно. Профиль рассчитывается автоматически после обработки событий; он не заполняется вручную. Если профиль ещё не появился, обновите список и проверьте источник/Analysis/Kafka.

Обратите внимание на размер выборки, покрытие наблюдений, распределения и статус достаточности данных. Отсутствие истории не означает обычное поведение. Включите **«История версий»** для просмотра сохранённых состояний. Переключатель **«Сравнить две версии»** открывает выбор «Было»/«Стало» и таблицы изменений. Для сравнения нужны две версии одной группы и совместимой методики; получить их можно после поступления нескольких операций.

### 3. Проверить объяснения отклонений

Откройте **«Операции»** и **«Предупреждения»**. В карточке доступны результат оценки и использованные данные. Исторический результат использует сохранённый порог и профиль, а не актуальные настройки, применённые задним числом. При отсутствии сохранённого порога интерфейс показывает неизвестное значение.

Текущая политика находится в `backend/contracts/assessment_policy.json`. Баллы складываются с ограничениями по группам проверок. Профиль описывает поведение, оценка описывает отклонение конкретной операции, а случай — процесс её рассмотрения: это разные сущности.

### 4. Рассмотреть случай

Руководитель распределяет доступные случаи. Войдите как **analyst**, откройте назначенный случай, возьмите его в работу, изучите операцию/оценку и добавьте комментарий. Завершите рассмотрение с решением «объяснена» или «нетипичная подтверждена», либо эскалируйте случай. Изменение прав или назначения влияет на доступ к материалам.

Подтверждённые решения передаются из Case в Analysis через Kafka. Последующие версии учитывают известные решения; старые профили и результаты не переписываются. Исходные операции при исключении из baseline не удаляются.

### 5. Проверить отчёты и администрирование

У руководителя откройте **«Отчёты»** или создание отчёта из карточки профиля/операции, выберите область и параметры. Сохранённый отчёт — снимок выбранных данных; повторная выгрузка не пересчитывает его по новому состоянию. Для экспорта доступны PDF/XLSX/CSV.

У **admin** раздел **«Сотрудники»** позволяет добавлять пользователей, менять роли, блокировать и разблокировать. После блокировки прежняя сессия не должна восстановиться при разблокировке: нужен новый вход. **«Состояние системы»** показывает готовность приложений и зависимости. **«Качество анализа»** у руководителя оценивает только синтетические сценарии, а не реальную банковскую точность.

## Где находится код

```text
backend/
  services/
    analysis/
      profiles/       # Расчёт, версии, сравнение, хранение, обновление
      assessments/    # Оценки операций, политика, запросы и чтение результатов
      application/    # Прикладные команды и запросы
      events/         # Обработка поступления операции
      feedback/       # Решения аналитика в Analysis
      persistence/    # Модели и репозиторий владельца
      reports/        # Данные владельца для отчётов
    transaction/
      ingest/         # Регистрация и пакетный импорт
      history/        # Поиск, группы клиентов, снимки истории
      demo/           # Демонстрационный источник и сценарии
      persistence/    # Собственное хранилище
      reports/        # Части отчётов
    case/
      lifecycle/      # Работа со случаем, команды, решения и обратная связь
      events/         # Приём результатов Analysis
      persistence/    # Случаи, комментарии, решения и уведомления
      reports/        # Снимки и метрики
      notifications.py
    auth/
      transport/      # HTTP и gRPC
      persistence/    # Учётные записи PostgreSQL
      service.py      # Пароли, роли, JWT и Redis-сессии
  gateway/            # GraphQL, сбор ответов и отчётов
  infrastructure/     # gRPC server/clients, Kafka, готовность, миграции
  contracts/          # GraphQL, JSON Schema, .proto, политика оценки
  generated/          # Скомпилированный Protobuf/gRPC
  common/             # Общие типы, валидация и контрактные функции
  reporting/          # Экспорт PDF/XLSX/CSV
frontend/             # Streamlit и экраны рабочих мест
infra/postgres/       # SQL по владельцам: auth/transaction/analysis/case
tests/                # Модульные, контрактные, UI и интеграционные проверки
tools/                # Настройка, тестовые стенды, проверка и обслуживание
```

| Задача разработчика | Точка начала |
|---|---|
| Регистрация / импорт операций | `backend/services/transaction/ingest/registration.py`, `commands.py` |
| Признаки профиля | `backend/services/analysis/profiles/metrics.py` |
| Сохранение версий / фоновое обновление | `backend/services/analysis/profiles/storage.py`, `refresh.py` |
| Сравнение версий | `backend/services/analysis/profiles/comparison.py`, `frontend/profile_comparison.py` |
| Оценка операции / сохранённые результаты | `backend/services/analysis/assessments/calculation.py`, `queries.py` |
| Решение по случаю | `backend/services/case/lifecycle/service.py` |
| Вход пользователя | `backend/services/auth/service.py`, `transport/http.py`, `transport/grpc.py` |
| Публичный API | `backend/contracts/schema.graphql`, `backend/gateway/` |

Точки запуска: Auth — `uvicorn backend.services.auth.transport.http:app --host 0.0.0.0 --port 8001`; Transaction/Analysis/Case — `python -m backend.infrastructure.server` с разными `SERVICE_NAME`, `DATABASE_URL` и необходимыми адресами/секретами. Полный набор переменных каждого процесса задан в `compose.yaml`.

При работающей инфраструктуре сервис обновляется отдельно:

```powershell
docker compose up -d --build --no-deps analysis-service
# Аналогично: auth-service, transaction-service, case-service, gateway, frontend.
```

`--no-deps` не поднимает недостающие зависимости. Для чистого запуска используйте общий запуск. Опубликованные gRPC-порты владельцев: Auth 51051, Transaction 51052, Analysis 51053, Case 51054. Приложения внутри Compose обращаются по именам сервисов на 50051.

## Базы данных и пароли

| Владелец | Порт с компьютера | База / пользователь | Host из pgAdmin внутри Compose |
|---|---|---|---|
| Auth | 57741 | bank_auth | auth-db |
| Transaction | 57742 | bank_transaction | transaction-db |
| Analysis | 57743 | bank_analysis | analysis-db |
| Case | 57744 | bank_case | case-db |

С компьютера Host — `127.0.0.1`; из контейнера pgAdmin используйте последнее поле таблицы и порт **5432**. Пароль PostgreSQL — `DB_PASSWORD` из локального `.env`. Вход в сам pgAdmin: `admin@bad-trans.example`, пароль `PGADMIN_PASSWORD`. Это два разных входа.

```powershell
.\tools\access.ps1 -Target PgAdmin -CopyPassword
.\tools\access.ps1 -Target Database -CopyPassword
```

При регистрации сервера в pgAdmin укажите соответствующие Host, порт, базу и пользователя из таблицы. Не используйте пароль приложения. Если том БД уже существовал, изменение POSTGRES_PASSWORD в `.env` не меняет пароль внутри PostgreSQL; согласуйте конфигурацию с существующей БД. Не удаляйте том для исправления входа.

SQL 001–004 используются при первоначальной инициализации. Последующие миграции владельцев применяются при запуске с журналом контрольных сумм. Применённые миграции не редактируют. Перед изменением схемы сохраните резервную копию и проверьте восстановление.

## Автоматические проверки

Для разработки нужен Python 3.13:

```powershell
.\tools\setup_python.ps1
.\tools\init_env.ps1
.\.venv\Scripts\python.exe -m pytest --collect-only -q
.\.venv\Scripts\python.exe -m pytest tests/profile_metrics tests/unit tests/system_health/test_health.py tests/product/test_behavior.py tests/product/test_boundaries.py -q
```

Этот набор проверяет вычисления, исторический порог, сравнение версий, права, контракты и UI без остановки продуктовых сервисов. Некоторые проверки вызывают Docker CLI; Docker Desktop должен работать. Тесты со специальными переменными окружения без отдельного стенда пропускаются. Collection использует importlib mode, поскольку в разных каталогах есть одноимённые тестовые файлы.

Для проверок хранения в отдельной PostgreSQL (образ `postgres:17-alpine` должен быть доступен):

```powershell
.\.venv\Scripts\python.exe tools/profile_storage_stand.py create --directory .local/profile-check
$env:PROFILE_STORAGE_STAND = (Resolve-Path .local/profile-check/stand.json).Path
try {
    .\.venv\Scripts\python.exe -m pytest tests/profile_storage -q
} finally {
    Remove-Item Env:PROFILE_STORAGE_STAND -ErrorAction SilentlyContinue
    .\.venv\Scripts\python.exe tools/profile_storage_stand.py cleanup --directory .local/profile-check
}
```

При повторении выберите новый каталог: утилита не перезаписывает существующий. Тесты отдельных процессов/Kafka требуют дополнительных runtime-настроек и могут быть пропущены даже при наличии тестовой PostgreSQL.

Проверки работающего стенда:

```powershell
.\.venv\Scripts\python.exe tools/verify.py
.\.venv\Scripts\python.exe tools/prove_flow.py
```

`verify.py` проверяет конфигурацию, доступность, контракты, таблицы и инфраструктуру. `prove_flow.py` создаёт синтетические записи и проверяет прохождение событий; это не проверка только чтением. Полный `run.ps1 -Action Test` дополнительно меняет тестовые данные, включает проверки отказов и временно останавливает контейнеры. Используйте его на отдельной тестовой установке; не запускайте одновременно с работой пользователей. Полный pytest включает интеграционные тесты, требующие подготовленного окружения.

## Если что-то не запускается

- Проверьте `docker info`, `docker compose ps --all` и `docker compose logs --tail 100 <service>`.
- При конфликте published port остановите другой стенд, занимающий этот порт, либо согласованно измените порты и внешние адреса в конфигурации.
- После изменения Python пересоберите затронутый образ; перезапуск старого контейнера не копирует новые файлы.
- Если операции зарегистрированы, но профилей нет, проверьте Analysis, Transaction и Kafka, очереди ошибок, состояние источника и затем обновите список в интерфейсе. При задержке сохранённые версии могут появиться не мгновенно.
- Различайте отсутствие готовности зависимости и остановку самого процесса. Для Gateway доступны `/livez` и `/readyz`; прикладная диагностика находится в рабочем месте администратора.
- `docker compose stop` сохраняет данные. `docker compose down -v` удаляет тома; для обычного перезапуска эта команда не нужна.
